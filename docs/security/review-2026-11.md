# Security review, 2026-11-24

Scope: the Convex backend (`apps/web/convex`), the web client (`apps/web/src`), deployment config and dependencies.
Method: read every public Convex function and its authorization, scanned the tree and git history for secrets, looked for
HTML injection sinks, ran `pnpm audit --prod`. Nothing was exploited against the live backend and no code has been changed.

## What is sound

- **Authorization on game data.** `game.save/resumeByCode/applyAction/get/log/listMine`, `highScores.save`,
  `bugReport.submit` and the multiplayer mutations all derive the caller from `getAuthUserId` and check ownership or seat
  membership. No function takes an identity argument.
- **Admin functions.** Every admin, analytics, story-admin and Test Mode function goes through `requireRole`/`requireAnyRole`,
  including `tryPrompt` (the paid API call). SYSTEM changes need SYSTEM. Sign-up, reset and verify flows are closed in
  `passwordProfile`; roles are never read from client params.
- **Server authority.** The score is recomputed server-side, stranger actions are refused from clients, `commit` and the
  other `v.any()` entry points are internal, and picks are validated server-side.
- **Invites.** Token is a random UUID, stored only as a SHA-256 hash, single use (claimed atomically, restored on failure),
  expires in 7 days, length-capped.
- **Secrets.** No keys or tokens in the tree or in git history (checked for the old Test Mode UUID, `sk-ant-`, GitHub and AWS
  token patterns). Only `VITE_CONVEX_URL`, `VITE_CONVEX_SITE_URL` and `VITE_BUILD_ID` reach the client.
- **HTML injection.** The only `dangerouslySetInnerHTML` (`carryRowHtml`) and the `innerHTML` writes in the legacy
  `cave3d.js`/`reveal.js` views take engine data (creature and item names), and `carryRowHtml` and the roster row escape it.
  Player-chosen text (party names, chat) is rendered by React. Bug-report text is neutralised before it goes into the issue.

## Findings

### 1. High: the client is sent the RNG seed and the deck order (leaderboard and multiplayer cheating)
`game.get` and `game.listMine` return the whole solo state, and `multiplayer.playView` returns `partyView`, which spreads in
`mp.cave`. That state holds `seed` (the LCG state), `largePack` and `smallPack`. A player can therefore run the engine
locally, predict every draw and die, search offline for a winning line, and replay it through `applyAction`. In multiplayer
it also shows a player the deck their rivals will draw from. The server recomputes the score, but it cannot tell a searched
game from a played one.
**Fix:** strip `seed` and the deck arrays (replace with their lengths) from `get`, `listMine`, `playView` and
`spectateView`. Check the client uses none of them: optimistic moves in the solo and multiplayer clients may rely on the decks
("decks included for optimistic moves" is in the `playView` comment), so that needs a design decision.
Note the replay endpoints (`replayByCode`, `highScores.log`) also expose the seed, but only for games already played.

### 2. High: dependencies with known advisories (FIXED 2026-11-24)
`pnpm audit --prod`: 1 critical, 2 high, 1 moderate, all through `@convex-dev/auth`.
- `@auth/core` <= 0.41.2: email normaliser validates before normalising (critical, GHSA-7rqj-j65f-68wh); `getToken()` throws
  on bad input (high, GHSA-xmf8-cvqr-rfgj); OAuth cookies not bound to the provider (moderate, GHSA-x445-f3h2-j279).
- `ws` < 8.21.0 via `convex`: memory exhaustion from tiny fragments (high, GHSA-96hv-2xvq-fx4p).
We use the Password provider keyed on a username, not the Email or OAuth providers, so exploitability looks low, but the fix
is cheap.
**Fixed:** `ws` is overridden to `>=8.21.0` in `pnpm-workspace.yaml`; `@convex-dev/auth` takes `@auth/core` as an exact peer, so
`@auth/core@0.41.3` is a direct dependency of `apps/web` (the override alone does not move a peer). `pnpm audit --prod` now reports
no known vulnerabilities.

### 3. Medium: bug reporting can be used to spam the public repo and fill storage
Anonymous sign-in is open to anyone, and each anonymous account is a new user. The limit of 5 reports an hour is per user, so
a script can mint accounts and file unlimited issues in the public GitHub repo. `generateUploadUrl` has no size, count or
rate limit, and the later checks only delete a bad file if it is referenced by a report. A file with no content type skips the
type check (`contentType !== undefined`). Screenshot URLs are public Convex storage URLs placed in a public issue.
**Fix:** a global cap on reports per hour (count `bugReports` by `by_created`), a per-user cap on outstanding uploads, treat a
missing content type as rejected, and a scheduled sweep that deletes unreferenced storage files.

### 4. Medium: no rate limits on other anonymous-reachable writes
`multiplayer.sendMessage` (chat), `joinByCode`, `createMultiplayer`, `newGame` and `highScores.save` (a name up to 40
characters, shown publicly) are limited only by sign-in, which is anonymous and free. Effects are storage growth and noise on
the leaderboard, not data exposure.
**Fix:** per-user limits on chat and game creation (the `@convex-dev/rate-limiter` component fits), and cap messages kept per
game.

### 5. Medium: no security headers (FIXED 2026-11-24)
`vercel.json` sets none: no Content-Security-Policy, `X-Content-Type-Options`, `Referrer-Policy` or frame protection
(`X-Frame-Options`/`frame-ancestors`), so the site can be framed and nothing limits script sources if an injection is ever
found. The legacy views use `innerHTML`, which makes a CSP worth having.
**Fixed:** `vercel.json` now sets a CSP (self-only scripts, no inline script, `frame-ancestors 'none'`, `object-src 'none'`;
styles allow inline for React style props and Google Fonts; connections to `*.convex.cloud`/`*.convex.site`), plus
`X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` and `Permissions-Policy`. Checked on a production build served with
these exact headers: splash and tutorial load, fonts and images load, Convex calls succeed, no console violations. Still worth
one look at the first Vercel preview, and the admin, bug-report screenshot and story download paths were not exercised.

### 6. Low: a four-letter code is a public key to replays
`replayByCode` is deliberately open to anyone with a code (26^4, about 457k values, enumerable). A guessed code reveals a
finished or in-progress solo game's moves and seed, and `testMode` games included. Live games make this a cheat route for
finding a seed (see 1) only for someone else's game, so the exposure is mostly privacy. `highScores.stats` and `log` read
whole event logs unpaginated and are public, so repeated calls cost reads.
**Fix:** restrict `replayByCode` to finished games, and consider a longer code. Cap or cache `stats`.

### 7. Low: password sign-in hardening to confirm
Password length is 10 to 128 and sign-up is closed, which is good. Confirm that `@convex-dev/auth`'s built-in limit on
failed sign-in attempts is active for the Password provider on this version (0.0.94), since admin accounts hold SYSTEM.
There is no second factor, which is acceptable for a beta but worth noting for SYSTEM accounts.

### 8. Low: stale bug-report `v.any()` and storage in the schema
`games.state`, `gameEvents.action/events` and `highScores.party/state` are `v.any()`. They are only written by trusted server
code today, so this is fine, but the validators give no protection if a future public function writes them.

## Suggested order

1. Dependency overrides (finding 2) and security headers (5): small and independent.
2. Strip seed and decks from client state (1): needs a decision on optimistic moves first.
3. Bug-report and chat limits (3, 4).
4. Replay by code (6) and the password limit check (7).

Anything touching Convex functions needs a deploy to the shared backend, which I will not run without asking.
